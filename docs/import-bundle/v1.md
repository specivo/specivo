# Import bundle format, version 1

An import bundle is how data from another tracker gets into Specivo. An importer (a separate
program, in any language) reads the source system and writes a bundle; Specivo validates the
bundle and loads it. Specivo knows nothing about the source system: everything it needs is in
the bundle, in the terms described here.

This page is the complete contract. The JSON Schemas in [`v1/`](v1/) describe the same records
machine-readably (JSON Schema draft 2020-12); where this page and a schema disagree, it is a bug
in one of them.

- Format name: `specivo-import-bundle`
- Version: `1.0`
- Schemas: `v1/*.schema.json`, `$id` `https://specivo.io/schemas/import-bundle/v1/<name>`

## Layout

A bundle is a directory, or a `.zip` archive whose entries are that directory's contents (the
files at the root of the archive, not inside a wrapping folder):

```
manifest.json          required: format version, source, generator, counts
lookups.json           trackers, statuses, priorities, activities, roles
users.jsonl            one record per line
groups.jsonl
projects.jsonl
memberships.jsonl
versions.jsonl
categories.jsonl
custom_fields.jsonl
issues.jsonl
journals.jsonl
relations.jsonl
wiki_pages.jsonl       each page with its whole history
wiki_redirects.jsonl
watchers.jsonl
attachments.jsonl      metadata only; the bytes are in files/
time_entries.jsonl
public_access.json
files/<sha256>         one file per distinct attachment content
```

Only `manifest.json` is required. Leave out any file the source has nothing for; an absent file
means "no records", never "keep what is there".

Anything else in the bundle is reported as a warning and ignored. In particular, **symbolic
links are refused** anywhere in a bundle, and a zip entry whose name is absolute, contains `..`,
uses a backslash or a drive letter, is a link or a device, or is encrypted makes Specivo refuse
the whole archive before anything is unpacked.

A zip is unpacked into a temporary directory before loading, so the machine running the import
needs free space for the unpacked bundle as well.

### Size limits

A bundle is untrusted input, so the reader stops at limits that a real migration stays well under
and that can be raised on the command line for one that does not. A bundle over a limit is
refused with a `too_large` problem; nothing is loaded.

| Limit | Default | Option | Applies to |
|---|---|---|---|
| Total unpacked size | 64G | `--max-unpacked-size` | a zip |
| Number of entries | 1000000 | `--max-entries` | a zip |
| Size of one entry | 16G | `--max-entry-size` | a zip |
| How far one entry may expand (unpacked size / stored size, for entries over 1M) | 200 | `--max-compression-ratio` | a zip |
| One JSON-lines record, newline included | 16M | `--max-line-size` | every bundle |
| `manifest.json`, `lookups.json`, `public_access.json` | 64M | `--max-json-size` | every bundle |

Zip limits are checked against the archive's headers first and again on the bytes actually
unpacked, so an archive that understates its sizes is caught too. Sizes take a `K`, `M` or `G`
suffix.

What the reader keeps in memory is bounded by these limits and by the number of records, not by
the size of the files: a JSON-lines file is read one line at a time and never held whole, the
three small JSON files are read whole (each at most the JSON limit), and the index of where each
record is takes one small entry per record.

## General rules

- **Encoding.** Every file is UTF-8, without a byte-order mark.
- **JSON lines.** A `.jsonl` file holds one JSON object per line, lines ending in `\n` (`\r\n`
  is tolerated). Blank lines are ignored. A record may not span lines: escape newlines inside
  strings as `\n`, as any JSON encoder does.
- **Unknown properties are errors.** Every record has a closed set of properties, so a typo is
  caught rather than silently dropped. Source data that has no property here goes into the
  record's `extra` object (see [below](#what-is-not-carried-over)).
- **`null` means absent.** For an optional property, writing `null` and leaving the property
  out are the same. Required properties may not be `null`.
- **Defaults.** An optional property left out takes the default given in its table.
- **Order.** Write records in any order. Specivo reorders what needs it: projects, issues and
  wiki pages are loaded parents first, and journal entries oldest first. Records that are
  already in a valid order keep that order, which matters for issues: Specivo numbers a
  project's issues (`KEY-1`, `KEY-2`, …) in the order they are loaded.

## Identifiers and references

Every record except watchers and wiki redirects has a **`source_ref`**: the record's identifier
in the source system, as a string.

- 1 to 255 characters, with no whitespace and none of `{`, `}`, `|` (so it can appear inside a
  placeholder). Schema: `common.schema.json#/$defs/sourceRef`.
- Unique per entity type, not across types: issue `"42"` and user `"42"` are unrelated.
- **Stable.** Exporting the same source twice must give each record the same `source_ref`.
  Specivo keeps a map from `source_ref` to the row it created, and that map is what makes
  loading a bundle twice create nothing the second time, and what lets a later bundle add the
  records created since the first one (a *delta* run). Use the source's own primary key, not a
  row number.

Records refer to each other by `source_ref`, in properties ending in `_ref` (one record) or
`_refs` (a list). Every reference must resolve to a record in the same bundle, of the type the
property names; validation reports any that does not. Three references to an issue are the
exception, so that a source exported in parts (one bundle per project, say) keeps the links
between its parts: an issue placeholder in text (see [Placeholders](#placeholders)), an issue's
`parent_ref` (see [issues.jsonl](#issuesjsonl)), and one end of a relation (see
[relations.jsonl](#relationsjsonl)). Each may name an issue of another bundle of the same source,
loaded before or after this one; the load looks it up among that source's imports and, if it is
not there yet, keeps the link in the [links file](#the-links-file) for the bundle that brings
it.

The entity types, each a namespace of `source_ref`s:

| Entity type | Records |
|---|---|
| `tracker`, `status`, `priority`, `activity`, `role` | the lists in `lookups.json` |
| `user` | `users.jsonl` |
| `group` | `groups.jsonl` |
| `project` | `projects.jsonl` |
| `membership` | `memberships.jsonl` |
| `version` | `versions.jsonl` |
| `category` | `categories.jsonl` |
| `custom_field` | `custom_fields.jsonl` |
| `issue` | `issues.jsonl` |
| `journal` | `journals.jsonl` |
| `relation` | `relations.jsonl` |
| `wiki_page` | `wiki_pages.jsonl` |
| `wiki_version` | the `versions` inside each wiki page |
| `attachment` | `attachments.jsonl` |
| `time_entry` | `time_entries.jsonl` |

The map is scoped by the source named in the manifest (`source.system` and `source.instance`,
both required), so bundles from two different installations never collide, and bundles from the
same one share it. **Reusing a `system`/`instance` pair means "add to the earlier import"**:
records already imported under that pair are skipped, only new ones are created. Two different
installations must therefore never share an instance name, and the import warns whenever the map
already holds records for the pair it is about to use, so a clash is noticed before it matters.
Changing `source.instance` between two exports of the same installation makes the second import
create everything again.

Because the bundle, not the operator, names the pair, adding to an earlier import is never
implicit: a load whose `system`/`instance` already has rows in the identifier map is refused,
naming the pair and what it holds, unless the command is given `--continue-import` (or `--resume`,
which continues a run). The refusal happens in `--dry-run` as well; `--validate` does not touch
the database and so cannot tell.

The pair is the identifier map's key: a bundle with `source.system` `redmine` and `source.instance`
`tracker.example.com` reads and writes the same rows as a Redmine import made with a version before
0.11.0, which read Redmine directly, run with `--source-instance tracker.example.com`. That is what
lets a tool's bundle carry on from a database such an import filled: give
the bundle the instance name that import used, or move the import to the bundle's name with
`python -m specivo.cli.admin import-map rename` (`import-map list` shows the scopes in a
database). `bundle` is reserved and cannot be a manifest's `source.system`.

## Value types

| Type | Written as | Example |
|---|---|---|
| timestamp | ISO 8601 date and time **with a UTC offset**; fractional seconds optional, up to 6 digits | `"2024-03-01T09:30:00+07:00"`, `"2024-03-01T02:30:00Z"` |
| date | ISO 8601 calendar date | `"2024-03-01"` |
| decimal | a JSON number, or a string of digits with an optional fraction and an optional leading `-` (exact). Where a property says "zero or more", a negative number is rejected. | `1.5`, `"1.333333"` |
| boolean | `true` / `false` | |
| integer | a JSON integer | |
| enum | one of the strings listed for the property | `"backlog"` |

Timestamps without an offset are rejected: Specivo stores time zone-aware timestamps and will not
guess. Original creation and update times are kept on the rows Specivo creates, so history reads
as it did in the source.

## Text, Markdown and placeholders

Text bodies are **Markdown** (CommonMark, plus GitHub-style tables and fenced code). The importer
converts the source's own markup (Textile, Jira wiki markup, ADF, HTML, …) before writing. The
fields that are Markdown are marked *Markdown* in the tables below. Specivo also understands:

- `[[Page title]]` and `[[Page title|text]]`: a link to a wiki page of the same project;
- `ACME-15`: an issue's display key, linked automatically;
- `![alt](diagram.png)` and `[spec](spec.pdf)`: a bare file name as a link target resolves to the
  attachment of that name on the same issue (in descriptions and comments) or in the same
  project (in wiki pages).

### Placeholders

An importer cannot know what a record will be called in Specivo: project keys are assigned by the
import, a login may be suffixed when it clashes with an existing one, a file is stored under a
new name. So text refers to other records by **placeholder**, and Specivo replaces each one after
everything is loaded:

| Placeholder | Becomes |
|---|---|
| `{{issue:REF}}` | the issue's display key: `ACME-15` |
| `{{issue:REF\|text}}` | a link to the issue reading *text*: `[text](/issue/ACME-15/)` |
| `{{user:REF}}` | a mention: `@login` |
| `{{attachment:REF}}` | the attachment's file name as a link target: `diagram.png`, or `<my diagram.png>` when the name has a space or bracket |
| `{{wiki:REF}}` | a link to the wiki page: `[[Title]]`, or a Markdown link when the page is in another project |
| `{{wiki:REF\|text}}` | the same, reading *text* |

`REF` is the referenced record's `source_ref`. An attachment placeholder is a link *target*, so
use it inside a link or image: `![screenshot]({{attachment:a-17}})`,
`[the log]({{attachment:a-18}})`. Only issue and wiki placeholders take a `|text`.

A label is text, never Markdown: brackets and backslashes in it are escaped, so it cannot close
the link early or point it somewhere else. A label may not contain `]]`, and one with a bracket, a backslash or
`|` turns `[[Title|text]]` into an ordinary Markdown link to the page.

Expanding a placeholder is not an edit: the record keeps the `updated_at` the bundle gave it.

Rules:

- Placeholders are expanded in issue descriptions, journal notes, the old and new values of
  description changes in journal details (`attr` / `description`), and wiki page text. In every
  other field text is stored exactly as written.
- Only the four kinds above are placeholders; any other `{{…}}` is ordinary text.
- Text inside fenced code blocks (```` ``` ```` or `~~~`) is never expanded, so a code sample can
  show a placeholder literally. Do not put placeholders there if you want them expanded. Fences
  pair as in CommonMark: a fence is a whole line of three or more backticks or tildes, indented by
  at most three spaces; the block ends at a line of the same character, at least as long, with
  nothing else on it, or else at the end of the text. Inline code spans are expanded like any
  other text.
- A user, attachment or wiki placeholder must name a record in the bundle; validation reports one
  that does not as an error (`unresolved_ref`).
- An issue placeholder may name an issue that is **not in the bundle**: a source exported in
  parts (one project at a time, say) refers to issues a previous bundle carried. On load it is
  looked up in the identifier map of the same source (`source.system` and `source.instance`),
  which holds every earlier import of that source; an issue another source imported, or the same
  `source_ref` under another instance, is never used. Validation cannot see the database, so it
  reports such placeholders as a warning (`external_ref`), one per file with the count and the
  first five refs, not as an error. The bundles can be loaded in any order (see
  [The links file](#the-links-file)); every load after the first needs `--continue-import`.
- A placeholder whose record was not imported, in this run or an earlier one of the same source
  (it is in neither the bundle nor the map, or it is in the bundle but was skipped with a
  warning), is written as plain text: its label if it has one (`{{issue:REF|the login bug}}`
  becomes `the login bug`), otherwise its bare `REF` (`{{issue:10388}}` becomes `10388`,
  `[log]({{attachment:a1}})` becomes `[log](a1)`). The placeholder syntax never reaches a reader.
  The import summary gives one warning for them all, with their number and the first ten. The
  import remembers such texts in its [links file](#the-links-file), and a later import of the
  same source that brings the records turns them into links.
- Each text is expanded in one pass: what a placeholder becomes is never expanded again.
- Specivo does **not** interpret source-specific reference syntax such as Redmine's `#123` in a
  bundle: write placeholders.

### The links file

A source exported in parts can be loaded in any order: a text that names a record of a bundle not
loaded yet is written as plain text first and becomes a link when that bundle is loaded, and a
relation or a parent naming an issue of a bundle not loaded yet is made when that bundle is
loaded. To do that, each load keeps a **links file**, a small SQLite database, by default next to
the bundle:
`specivo-links.<system>.<instance>.sqlite`, where `<instance>` is the manifest's
`source.instance` made safe for a file name (characters other than letters, digits, `.`, `_`
and `-` become `-`, and a short hash of the original is appended when anything had to change).
`--links-file PATH` puts it elsewhere. Give every load of the source the same file.

- **What it holds.** Three kinds of rows, each waiting for a record that was not imported:
  - a **text**: one row per imported text still naming such a record: which row and column it is
    (an issue description, a journal note, the old or new value of a description change, a wiki
    revision), its source text with the placeholders, a SHA-256 of the text Specivo wrote, and the
    placeholders still waiting (`kind`, `ref`);
  - a **relation** with an end that was not imported, as the bundle wrote it: its `source_ref`,
    `from_ref`, `to_ref`, `relation_type` and `delay`;
  - a **parent**: an imported issue whose `parent_ref` names an issue that was not imported, as the
    two `source_ref`s.

  A `meta` table names the format version and the scope (`source.system`, `source.instance`).
- **On every load,** in the relations phase, each waiting parent whose issue is now in the
  identifier map is set, and then each waiting relation whose two issues are is made, with the
  same checks as any parent or relation (see [issues.jsonl](#issuesjsonl) and
  [relations.jsonl](#relationsjsonl)); one Specivo refuses is skipped with a warning and leaves the
  file. Later, after the placeholders of the bundle itself are expanded, each waiting text whose
  records are now in the identifier map is expanded again from its source text and written,
  keeping `updated_at`. What is still missing stays in the file: a text stays plain text, a
  relation stays unmade, an issue stays without its parent. The summary counts what it linked and
  what still waits.
- **Each link is made once.** A relation is recorded in the identifier map by its `source_ref`, so
  one that two bundles carry is made by whichever load first has both issues, and the other load
  skips it; a waiting row for a relation that exists is dropped. Loading a bundle again never
  makes a relation or sets a parent twice.
- **Edited text is never overwritten.** If the text in Specivo no longer matches what the import
  wrote (somebody edited the description, say), it is left as it is, dropped from the file, and
  reported in a warning with the number and the first few rows. Editing a wiki page adds a new
  revision, so only the imported revisions are linked. In the same way a waiting parent is set
  only on an issue that has no parent: if the issue has been given another parent since it was
  imported, that one is kept, the row is dropped, and a warning names the issue.
- **Not trusted.** The file lives next to the bundles, so whoever supplies those can supply it.
  Every row is signed with an HMAC-SHA256 keyed from the server's `SECRET_KEY`, over the scope,
  the kind of row and all it holds (for a text the row and column, the source text and the hash);
  a row without a valid signature, one naming any column but those listed above or holding a
  malformed ref or relation type, and one naming a row this source's identifier map does not hold
  are ignored, removed from the file and counted in a warning. Relations and parents name issues
  by `source_ref` only, and are looked up in the identifier map of the file's scope, so they can
  only ever link issues that import brought in. A links file therefore only
  works with the Specivo installation, and the `SECRET_KEY`, that wrote it. A links file that is
  a symbolic link, or that turns into one while it is being opened, is refused with a warning;
  a new one is created readable by its owner only (mode 0600), since it holds source texts.
  Keep the folder that holds it writable by the operator only: anyone else who can write there
  can still race the file or its journal, which is the risk that remains.
- **One transaction.** The file is changed in one SQLite transaction that is committed only after
  the database transaction it describes; a load that fails leaves it as it was. When nothing is
  left waiting, the file is deleted.
- **A throwaway.** Losing the file, or deleting it after cut-over, only means those references
  stay plain text. A file that cannot be read is reported and ignored, and so is a location that
  cannot be written (a read-only mount, say): the import succeeds, and its unresolved references
  will not be linked later. A file of another scope, or of an unknown format version, is refused
  before anything is imported.
- `--dry-run` reads the file and reports what would be linked, and writes nothing. `--validate`
  does not read it.
- Outside an import, `admin import-map pending --links-file PATH` counts what is waiting (texts,
  relations and parents), and `admin import-map resolve-pending --links-file PATH --yes` links
  what can be linked now, parents first, then relations, then texts.

## manifest.json

Schema: `manifest.schema.json`.

```json
{
  "format": "specivo-import-bundle",
  "format_version": "1.0",
  "source": {"system": "jira", "instance": "tracker.example.com", "version": "9.12"},
  "generator": {"name": "specivo-jira-migration", "version": "0.1.0"},
  "exported_at": "2024-03-01T09:30:00Z",
  "counts": {"users": 12, "projects": 2, "issues": 340},
  "not_carried_over": [
    {"what": "Sprint boards have no equivalent", "count": 4}
  ]
}
```

| Property | Type | Required | Meaning |
|---|---|---|---|
| `format` | `"specivo-import-bundle"` | yes | Identifies the file as a bundle. |
| `format_version` | string `MAJOR.MINOR` | yes | The format version the bundle follows: `"1.0"`. See [Versioning](#versioning). |
| `source.system` | string, `^[a-z][a-z0-9_]{0,29}$` | yes | The source product, lower case. |
| `source.instance` | string, 1–200 characters | yes | Which installation, e.g. its host name. Scopes the identifier map: a later bundle with the same `system` and `instance` adds to the earlier import (see [Identifiers and references](#identifiers-and-references)). Do not put credentials in it. |
| `source.version` | string | no | The source product's version, for the record. |
| `generator.name`, `generator.version` | strings | yes | The program that wrote the bundle. |
| `exported_at` | timestamp | yes | When the export was taken. |
| `counts` | object | no | Records per file, by file name without `.jsonl` (`"issues"`), plus `trackers`, `statuses`, `priorities`, `activities`, `roles` for the lists in `lookups.json` and `wiki_versions` for the revisions inside wiki pages. Every count given is checked against the files; a mismatch (a truncated file, say) is an error. Write them all. |
| `not_carried_over` | array | no | What the importer could not express in the bundle, see [below](#what-is-not-carried-over). |

The identifier map is keyed by `source.system` and `source.instance`; `--source-instance` on the
command line overrides the instance. `source.system` must not be `bundle` (reserved).

## lookups.json

Schema: `lookups.schema.json`. One object with up to five lists, each optional:

```json
{
  "trackers": [{"source_ref": "1", "name": "Bug", "default_status_ref": "10"}],
  "statuses": [{"source_ref": "10", "name": "Open", "category": "backlog"}],
  "priorities": [{"source_ref": "3", "name": "Normal", "is_default": true}],
  "activities": [{"source_ref": "9", "name": "Development", "is_default": true}],
  "roles": [{"source_ref": "4", "name": "Developer"}]
}
```

An issue needs a tracker, a status and a priority, so a bundle with issues needs all three
lists. A time entry needs an activity.

What happens when Specivo already has a lookup of the same name: statuses, trackers and priorities
get a second row unless the operator passes `--merge-duplicate-statuses`; activities and roles are
always matched by name, since Specivo's names are unique. Every collision is reported.

|---|---|---|---|
| `source_ref` | ref | required | |
| `name` | string | required | |
| `description` | string | none | |
| `is_in_roadmap` | boolean | `true` | Issues of this type appear on the roadmap. |
| `default_status_ref` | `status` ref | none | Status new issues start in. |
| `disabled_core_fields` | array of strings | `[]` | Issue fields hidden for this type, any of: `assigned_to_id`, `category_id`, `fixed_version_id`, `parent_id`, `start_date`, `due_date`, `estimated_hours`, `done_ratio`, `description`, `priority_id`. |
| `position` | integer | `0` | Sort order. |
| `private_by_default` | boolean | `false` | New issues of this type start private. |
| `extra` | object | | |

### statuses

| Property | Type | Default | Meaning |
|---|---|---|---|
| `source_ref` | ref | required | |
| `name` | string | required | |
| `category` | `backlog` \| `active` \| `done` \| `closed` | required | Specivo's grouping: not started, in progress, finished but not closed, closed. A source with only "open/closed" must decide; let the operator override the guess. |
| `position` | integer | `0` | |
| `default_done_ratio` | integer 0–100 | none | |
| `extra` | object | | |

### priorities

`source_ref` (required), `name` (required), `position` (integer, `0`), `is_default` (boolean,
`false`), `active` (boolean, `true`), `extra`.

### activities (time tracking)

`source_ref` (required), `name` (required), `is_default` (boolean, `false`), `active` (boolean,
`true`), `extra`.

### roles

| Property | Type | Default | Meaning |
|---|---|---|---|
| `source_ref` | ref | required | |
| `name` | string | required | |
| `builtin` | `0` \| `1` \| `2` | `0` | `0` an ordinary role; `1` the role signed-in non-members hold on public projects (matched to Specivo's own, never created); `2` the anonymous role (not created: anonymous access is per project, see [public_access.json](#public_accessjson)). |
| `permissions` | array of strings | `[]` | Kept for the record only. Roles are created **without** permissions and listed for an administrator to fill in, because no source's permission names mean exactly what Specivo's do. |

| `time_entries_visibility` | `all` \| `own` | Specivo's default | Whose logged time they can see. |
| `extra` | object | | |

## Record files

Each section lists the record's properties. "ref → X" means a `source_ref` of an X record.
Every record may also carry an `extra` object (not repeated below).

### users.jsonl

Schema: `users.schema.json`. People only: groups go in `groups.jsonl`, and anonymous or system
accounts are left out.

| Property | Type | Default | Meaning |
|---|---|---|---|
| `source_ref` | ref | required | |
| `login` | string, non-empty | required | Kept where possible; suffixed (`-2`) if Specivo already has it, which is reported. |
| `display_name` | string | required | Full name. |
| `email` | string | none | An account without one gets a placeholder address in the reserved `invalid` domain (`login@invalid`), so no mail reaches anyone; it is reported. |
| `status` | `active` \| `locked` \| `pending_verification` \| `deactivated` | `active` | Every account that is not `active` is listed in the report. |
| `is_admin` | boolean | `false` | The account administers the source. **Not carried over by default**: the account is imported as an ordinary one and listed in the report, unless the operator passes `--import-admins`. |
| `language` | string | instance default | A language code such as `th`; one this instance does not ship falls back to its default. |
| `last_login_at`, `created_at`, `updated_at` | timestamp | none | |
| `credential` | object | none | The source's stored password, see below. |
| `must_change_password` | boolean | `false` | Used only when the credential is carried over. |
| `password_changed_at` | timestamp | none | Used only when the credential is carried over. |
| `external_auth` | boolean | `false` | The account signs in through an external directory (LDAP) and has no local password. Reported. |

By default every imported account must set a new password at first sign-in. `credential` lets an
account keep its old one, only when the operator passes `--import-passwords` **and** has enabled
a hasher for the algorithm (`LEGACY_PASSWORD_ALGORITHMS`); administrators never keep theirs.
`credential.algorithm` names the hasher (`redmine_sha1`, or one a plugin provides) and
`credential.fields` (string to string) holds the source's raw credential columns under the names
that hasher reads. **A bundle with credentials holds secrets**: protect it like a password
database, and leave `credential` out unless passwords are meant to move. A `credential` that
does not match its schema is reported without its value, as

## Attachments and files/

The bytes of every attachment are stored once under `files/`, named by the lower-case hex SHA-256
of the content: two attachments with the same content share one file. `files/` holds nothing
else; a file no attachment refers to is a warning and is not imported.

Validation hashes every referenced file: a missing file or one whose bytes do not hash to its name
is an error. Write a file's bytes first, hash them as you write, and use that hash; do not hash a
different copy.

### A directory, and files kept apart

A bundle may be a plain directory as well as a `.zip` of one, and for a migration with many
attachments a directory is the better container: Specivo unpacks a zip into a temporary directory
first (so it needs room for the zip, the unpacked copy and the stored files), attachments are
mostly compressed already, and a directory can be copied with `rsync`, which resumes and skips
files already there. Because files are named by their hash, a later export only adds new ones.

The stored files can also live apart from the records. With `--files-path DIR` Specivo reads
`<DIR>/<sha256>` instead of `files/<sha256>`; the bundle (a directory or a zip holding only the
records) needs no `files/` at all:

```
python -m specivo.cli.import_data --source bundle --path data.zip --files-path /srv/export/files --validate
```

The directory gets the same checks as `files/` inside a bundle, and problems are reported under
the same names (`files/<sha256>`) and codes:

- a referenced file that is absent (`missing_file`) or whose bytes do not hash to its name
  (`hash_mismatch`) is an error on the attachment's line; a `filesize` that differs is a warning;
- a symbolic link anywhere inside the directory is an error (`symlink`) and nothing else is read.
  The directory itself may be a link, which is resolved once;
- a pipe, device or socket in it, or a directory named like a stored file, is an error
  (`unsafe_entry`) and nothing else is read;
- anything that is not a `<sha256>` file is ignored with an `unknown_file` warning, and a stored
  file no attachment uses gives the usual `unreferenced_file` warning;
- a directory that does not exist, is not a directory, or is inside the bundle or contains it, is
  an `unreadable` error and nothing is read;
- if the bundle has a `files/` of its own as well, that is ignored (and not unpacked from a zip),
  with an `unknown_file` warning on `files`.

Nothing in the format changes: the manifest does not say where the files are.

## What is not carried over

Nothing the source had should disappear silently. Two places record it:

- **`extra`**, on any record: an object holding source data that has no property in this format,
  kept with the record it belongs to. Specivo does not import it; the report counts the records
  that have one, so the operator knows the bundle holds more than was loaded. Use it for
  anything you would otherwise drop: a source field without an equivalent, the original markup
  of a field you converted, a raw status name.
- **`not_carried_over`**, in the manifest: things that are not part of any record, one entry per
  item or per kind, each `{"what": "…", "count": n, "entity_type": "…", "source_ref": "…"}` where
  only `what` is required. Specivo prints them in the import report. Use it for whole features
  without an equivalent (boards, forums), records you skipped (attachments on a forum post), and
  files you could not read.

## Validation

Specivo checks the whole bundle before loading anything, and refuses to load a bundle with any
error. The same check runs on its own with `--validate`:

```
python -m specivo.cli.import_data --source bundle --path export.zip --validate
```

It reads only the bundle (no database), prints a report and exits `0` when the bundle is valid,
`1` when it is not. `--report-json PATH` also writes the report as JSON. Each problem names the
file and, for a `.jsonl` file, the line (1-based); for a `.json` file, a JSON pointer:

```
issues.jsonl:17: error: author_ref: no user with source_ref '10442' [unresolved_ref]
manifest.json#/counts/issues: error: The manifest counts 340 issues but the bundle holds 339 [count_mismatch]
attachments.jsonl:3: warning: filesize says 2048 bytes but files/9f86…08 holds 2050; the real size is kept [size_mismatch]
issues.jsonl: warning: 2 issue placeholder(s) name no issue in this bundle, e.g. '10388' (line 4), '10391' (line 9); loading looks them up in earlier imports of the same source and writes any it cannot find as plain text [external_ref]
relations.jsonl: warning: 1 relation end(s) name no issue in this bundle, e.g. '20114' (line 3); loading looks them up in earlier imports of the same source and keeps any relation it cannot make yet in the links file until a later import brings the issue [external_ref]
```

| Code | Severity | Meaning |
|---|---|---|
| `unreadable` | error | Not a directory or a readable zip archive, a file of the bundle that cannot be read, or a `--files-path` that is not a directory or overlaps the bundle. |
| `unsafe_entry` | error | A zip entry with an absolute or `..` path, a backslash or drive letter, a device, an encrypted entry, or a duplicate name; in a directory bundle, a pipe, device, socket or directory under a file name the format reads, or in `files/`. |
| `too_large` | error | Over one of the [size limits](#size-limits): the archive, an entry, a JSON-lines record or a JSON file. |
| `symlink` | error | A symbolic link in the bundle or the archive. |
| `unknown_file` | warning | A file that is not part of the format; ignored. Also the bundle's own `files/` when `--files-path` is given. |
| `unsupported_version` | error / warning | Not a bundle, or an unsupported major version (error); a newer minor version (warning). |
| `invalid_json` | error | A line or file that is not valid JSON or not UTF-8. |
| `schema` | error | A record that does not match its schema; a date or timestamp that does not exist (`2024-02-30`); wiki revisions out of order. |
| `duplicate_ref` | error / warning | A `source_ref` used twice for one entity type, or a redirect listed twice (error); a watcher listed twice (warning). |
| `unresolved_ref` | error | A reference or placeholder naming a record that is not in the bundle (an issue placeholder, an issue's `parent_ref` and one end of a relation are `external_ref` instead). |
| `external_ref` | warning | Issue references naming issues that are not in the bundle: issue placeholders, `parent_ref`s in `issues.jsonl`, and relation ends in `relations.jsonl`. One warning per file and kind, on the file, with how many there are and the first five refs and their lines. The load looks them up in the imports of the same source; a placeholder it cannot find is written as plain text, its label or else its ref (see [Placeholders](#placeholders)), and a parent or relation it cannot make yet is kept in the [links file](#the-links-file). |
| `invalid_ref` | error / warning | A reference that resolves but cannot be right: a custom value's key differs from its field's, two custom fields share a key, a self-relation, a relation with neither end in the bundle, a wiki parent in another project, a label on a user or attachment placeholder, a label containing `]]` (errors); an issue assigned to a group (warning). |
| `parent_cycle` | error | Projects, issues or wiki pages whose `parent_ref`s form a loop, an issue that is its own parent among them; issues are checked across projects. |
| `missing_file` | error | An attachment whose `files/<sha256>` is not in the bundle, or no manifest. |
| `hash_mismatch` | error | A stored file whose bytes do not hash to its name. |
| `size_mismatch` | warning | An attachment's `filesize` differs from its file. |
| `unreferenced_file` | warning | A file in `files/` no attachment uses. |
| `count_mismatch` | error | A manifest count that does not match the records. |

Validation checks the bundle, not the target: it cannot know that a login is taken or that a
project key exists. Those are settled by the load and reported by `--dry-run`.

## Loading a bundle

```
# check the bundle
python -m specivo.cli.import_data --source bundle --path export.zip --validate
# rehearse: the whole import in a transaction that is rolled back, then the report
python -m specivo.cli.import_data --source bundle --path export.zip --dry-run
# import
python -m specivo.cli.import_data --source bundle --path export.zip
```

The run options are the same as for every import source (`--help` lists them):
`--merge-duplicate-statuses`, `--project-key-map`, `--project`, `--import-passwords`,
`--import-admins`, `--flatten-excess-depth`, `--strict`, `--report-json`, `--resume`, and the
[size limits](#size-limits). `--files-path DIR` reads the stored files from a directory of their
own (see [above](#a-directory-and-files-kept-apart)).

- **Dry run.** Every phase runs against the database inside one transaction that is always rolled
  back, and no files are copied, so the report shows exactly what an import would do: the
  project keys chosen, collisions, what was skipped and why.
- **Idempotent.** Loading the same bundle again with `--continue-import` creates nothing: every
  record is found in the identifier map and skipped. A run that stopped half way continues where
  it left off with `--resume`.
- **Delta runs.** A later export of the same source, with the same `system`, `instance` and
  `source_ref`s, loaded with `--continue-import`, adds the records created since; records already
  imported are skipped, not updated. Without the flag a load into a `system`/`instance` that
  already has rows is refused, so a bundle cannot attach its records to another import's by
  naming its source. A run that adds to an earlier import says so in a warning. A later bundle's
  issue placeholders, issue parents and relations may name issues of an earlier one; the
  placeholders are expanded to those issues' keys, and the parents and relations are made. An
  earlier bundle's references, parents and relations naming records the later one brings are
  linked through the [links file](#the-links-file).
- **Records without an author** (`author_ref` absent or naming a user who was not imported) are
  attributed to an import service account named after the source system, `<system>-import`
  (`redmine-import` for a Redmine bundle, the same account an earlier direct Redmine import created). Only an
  account an import created is reused under that name; if the login belongs to anyone else, a
  person or another service account, the import uses `<system>-import-2` (or the next free
  number) and says so in a warning.
- **Warnings do not stop an import.** Anything Specivo cannot load as given (a relation it
  refuses, a time entry without an activity) is skipped and listed. Relations and parents that
  wait for another bundle's issue are counted in one warning. `--strict` turns every
  warning into a failure, for testing an importer.

## Fields that came from Redmine

The format is derived field by field from the intermediate representation Specivo's importer has
used since its first source, Redmine. A unit test keeps the schemas and that representation in
step. Where a field came from Redmine, this is the decision taken for the format:

| Field | Decision |
|---|---|
| attachment `storage_key` (Redmine's path under its files directory) | Replaced by `sha256` and `files/<sha256>`. |
| issue references written `#123` | Not interpreted in a bundle: write `{{issue:REF}}`, also for an issue exported in an earlier bundle of the same installation. |
| `attachment:name`, `user:login` macros | Converted by the importer: `{{attachment:REF}}`, `{{user:REF}}`. |
| project `status` 1/5/9 | Kept: it is also Specivo's encoding. |
| project `modules` | Kept, limited to Specivo's module names. |
| role `builtin` 0/1/2 | Kept: Specivo's encoding of ordinary, non-member and anonymous. |
| role `permissions` | Kept, optional, for the record: roles are created without permissions. |
| role `users_visibility`, `time_entries_visibility` | Kept, optional: Specivo uses Redmine's values. |
| tracker `disabled_core_fields` | Kept, optional, in Specivo's field names. |
| version `sharing` | Kept, optional: same vocabulary as Specivo. |
| custom field `field_format` | Kept: free text, only `user` and `version` mean something to Specivo. |
| journal detail `property`/`prop_key` | Kept: Specivo's journal details use the same vocabulary. Values naming a record are refs (`old_ref`, `new_ref`), not the source's ids. |
| user `credential` | Kept, optional: generic (an algorithm name and fields), Redmine's is one algorithm. |
| user `external_auth` (LDAP) | Kept, optional. |
| `public_access` | Kept as an optional file, already in Specivo's terms; most sources leave it out. |
| status `category` | Kept, required: Specivo's four-way grouping; every source has to map to it. |

## Versioning

`format_version` is `MAJOR.MINOR`.

- A **minor** version only adds optional properties or files. A reader that knows `1.0` loads a
  `1.1` bundle, ignoring what it does not know, with a warning saying so.
- A **major** version is anything else. Specivo refuses a bundle whose major version it does not
  support, before reading anything but the manifest.

Write the lowest version that has everything your bundle uses: `"1.0"`.

## A minimal bundle

The smallest useful bundle: one user, one project, one issue with a comment and an attachment.

`manifest.json`

```json
{
  "format": "specivo-import-bundle",
  "format_version": "1.0",
  "source": {"system": "sample", "instance": "tracker.example.com"},
  "generator": {"name": "sample-exporter", "version": "1.0.0"},
  "exported_at": "2024-03-01T09:30:00Z",
  "counts": {"trackers": 1, "statuses": 1, "priorities": 1, "users": 1, "projects": 1,
             "issues": 1, "journals": 1, "attachments": 1}
}
```

`lookups.json`

```json
{
  "trackers": [{"source_ref": "bug", "name": "Bug", "default_status_ref": "open"}],
  "statuses": [{"source_ref": "open", "name": "Open", "category": "backlog"}],
  "priorities": [{"source_ref": "normal", "name": "Normal", "is_default": true}]
}
```

`users.jsonl`

```json
{"source_ref": "u1", "login": "alice", "display_name": "Alice Example", "email": "alice@example.com"}
```

`projects.jsonl`

```json
{"source_ref": "p1", "identifier": "web", "name": "Website", "created_at": "2023-01-10T08:00:00Z"}
```

`issues.jsonl`

```json
{"source_ref": "web-1", "project_ref": "p1", "tracker_ref": "bug", "status_ref": "open", "priority_ref": "normal", "subject": "Login fails", "author_ref": "u1", "description": "Steps are in ![the screenshot]({{attachment:a1}}).", "created_at": "2024-02-01T10:00:00Z"}
```

`journals.jsonl`

```json
{"source_ref": "c1", "issue_ref": "web-1", "user_ref": "u1", "notes": "Reproduced, {{user:u1}}.", "created_at": "2024-02-02T10:00:00Z"}
```

`attachments.jsonl`, with the file's bytes in `files/<sha256>`

```json
{"source_ref": "a1", "container_kind": "issue", "container_ref": "web-1", "filename": "screenshot.png", "sha256": "<sha256 of the bytes>", "content_type": "image/png", "author_ref": "u1", "created_at": "2024-02-01T10:00:00Z"}
```

A complete example covering every file is in the Specivo repository under
`tests/fixtures/import_bundle/full/`.
